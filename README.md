# Vendor Performance & Risk Analysis

An end-to-end procurement analytics project: vendor KPIs, a weighted scoring model with adjustable weights, KMeans vendor segmentation, a calibrated late-delivery classifier, and an interactive Flask dashboard.

## Problem Statement

A procurement team buys from dozens of vendors. Some deliver late, some ship defective goods, some charge well above market, and the spreadsheet view hides all of it. The team needs to know which vendors are reliable, which are risky, and which upcoming orders are likely to arrive late.

## Objectives

- Compute standard procurement KPIs per vendor.
- Combine them into a single 0-100 score whose weights the user can change.
- Segment vendors into Good / Average / Watchlist / Risky groups.
- Predict whether a new order will be late, with a probability that means something.
- Present all of it in a dashboard with recommendations drawn from the calculated results.

## Dataset

**The data is synthetic**, generated by `src/data_generation.py` (seeded, reproducible). No public dataset had promised date, actual date, defective quantity and support response time together.

- 30 vendors, about 4,000 orders (Jan 2024 to Dec 2025), 6 categories.
- Each vendor has a hidden profile (reliable, average, late-prone, defect-prone, expensive) that drives delay probability, defect rate, price level and support speed.
- Delay probability also depends on category, quantity, tight lead times and an Oct-Dec rush.
- About 2-3% missing values, ~2% duplicate rows, negative quantities and prices, unparsable and impossible dates, price outliers and messy vendor IDs are injected on purpose so the cleaning stage is meaningful.

Because the data is synthetic, the patterns are in the data by design; they are not real-world discoveries. The pipeline runs unchanged on a real CSV with the same columns.

## Data Cleaning

Nothing is dropped silently. Every step is written to `data/processed/cleaning_log.csv`.

- Duplicates removed (exact rows and repeated order IDs).
- Rows with unparsable dates, or a delivery date before the order date, cannot yield an honest `is_late`; they are saved to `rejected_rows.csv` instead of being guessed.
- Negative quantities and prices are treated as sign errors and flipped.
- Prices above 2.5x market price are treated as entry errors and re-imputed.
- Missing quantities, prices, shipping cost and response time are imputed with vendor-level (or category-level) medians so vendor differences are not flattened.
- Derived fields: `lead_time`, `delivery_delay_days`, `is_late`, `fill_rate`, `defect_rate`, `price_variance`.

## KPI Framework

| KPI | Definition |
|---|---|
| On-time delivery rate | on-time orders / total orders |
| Average delay | mean delay in days; early deliveries count as 0 so they never distort it |
| Defect rate | defective units / received units (quantity weighted) |
| Fill rate | received units / ordered units |
| Price variance | mean % gap between vendor unit price and the order's **market price** benchmark |
| Complaint response time | mean support response time (hours) |

## Vendor Scoring

Each KPI is min-max normalised across vendors to 0-1 (flipped for "lower is better" KPIs) so different units can be combined. KPIs are grouped into Delivery (on-time, delay), Quality (defects, fill), Cost (price variance) and Support (response time). Default weights are 30 / 30 / 25 / 15. The score is the weighted sum scaled to 0-100. Min-max is sensitive to extreme vendors, which is an accepted trade-off for an interpretable score.

## Machine Learning

**KMeans.** Six vendor KPIs are standardised. k was tested from 2 to 8 with inertia and silhouette. Only k in 3-5 with no cluster smaller than 3 vendors was allowed (higher silhouette at k=6-7 came from tiny clusters), which selected **k = 5**. Labels come from each cluster's average vendor score, not from the cluster number.

**Late-delivery classification.**
- Features known at order time: quantity, price, price vs market, promised lead time, vendor, category, region, payment terms, month, plus vendor history.
- Leakage control: for each order, history uses only that vendor's earlier orders that were **already delivered before the order date**. Actual delivery date, delay, received/defective quantity and complaints of the order itself are never features.
- Chronological split: train on the oldest 75% of orders (to 2025-06-30), test on the newest 25%.
- Imbalance: about 32% of orders are late, which is moderate, so `class_weight` is used and no oversampling.
- Logistic Regression and Random Forest were compared with time-series cross-validation on the training window (CV ROC-AUC 0.718 vs 0.721, effectively a tie). Random Forest was selected and then calibrated with `CalibratedClassifierCV` (sigmoid). Calibration lowered the test Brier score from 0.206 to 0.197.
- A single sklearn `Pipeline` (imputation, scaling, one-hot encoding, model) takes raw inputs. The deployed model is refit on all orders after evaluation.

**Test results (newest 993 orders, calibrated Random Forest).** ROC-AUC 0.70.

| Threshold | Accuracy | Precision | Recall | F1 |
|---|---|---|---|---|
| 0.50 | 0.71 | 0.74 | 0.26 | 0.38 |
| 0.35 (used in app) | 0.65 | 0.50 | 0.53 | 0.51 |

Missing a late order is usually costlier than an extra follow-up call, so the app flags orders at a 35% calibrated probability. That trades precision for recall (0.26 to 0.53). The model is a moderate risk-ranking aid, not a precise predictor.

**Interpretability.** Permutation importance on the test window ranks `hist_avg_response`, `hist_defect_rate` and `order_month` highest. Response time and defect history most likely act as proxies for overall vendor quality. Importances are small in absolute terms.

## Dashboard

- **Home:** KPI cards, adjustable weights (POST form, server-side validation that the total is exactly 100), vendor ranking, risk-group distribution and profile, monthly trend, category performance, top problematic vendors, business insights.
- **Vendors:** pick a vendor to see score, rank, all KPIs, risk group, monthly trend, component scores vs average and delay distribution.
- **Prediction:** enter vendor, category, quantity, month, price and lead time; get YES/NO plus a calibrated probability. Vendor history is filled from real past data.

## Key Business Insights

From the generated dataset (results change if you regenerate with another seed):

- The overall late rate is about 33%. Kestrel Traders (V020), Nova Supplies (V013) and Unity Industries (V030) are late on 74-79% of orders.
- Dynamo Components (V001) has the highest defect rate at 7.8% against a 2.5% median.
- Four vendors charge about 22% above market; all four still deliver above the median on-time rate, so the premium may partly buy reliability.
- Electronics has the highest late rate (40%) and Packaging the lowest (17%).
- Oct-Dec orders are late 41% of the time versus 30% in other months.
- Four vendors form the Risky cluster with an average on-time rate of about 25%.

Recommendations in the dashboard (closer monitoring, SLA review, quality audits, earlier year-end ordering) are generated from these calculated values.

## How to Run

```bash
python -m venv venv
venv\Scripts\activate          # Windows
# source venv/bin/activate     # macOS / Linux
pip install -r requirements.txt

python train.py                # data -> cleaning -> KPIs -> models (add --regenerate for fresh data)
python app.py
```

Open http://127.0.0.1:5000 in your browser. The EDA notebook is in `notebooks/eda.ipynb` (run `jupyter notebook`).
